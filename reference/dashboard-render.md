# Dashboard render contract

The ONLY binding contract for every render of `context/today.html` — whether a full `/morning` run or a mid-day update from the chat (CLAUDE.md rule 1). **For a mid-day update this file plus the changed context files plus `context/.mail_cache.json` is enough — never load the /morning skill for that.**

## Core principles

- **Never regenerate the HTML/CSS shell.** The static shell lives once in `context/today_template.html` — only touch it when the design changes. Every render fills only the dynamic parts and writes `today.html` — **overwrite, always, never copies/archives**. State lives in the files, not in the HTML.
- **NEVER read the template into context.** The fill script reads it mechanically via string replace — Claude only produces the short fragments. If you exceptionally need one spot out of it (e.g. the comment block at the `{{AUSSTATTUNG}}` placeholder), pull the affected lines specifically via `grep -n`, never the whole file.
- **Read-only:** no write interaction in the dashboard. Everything operational runs in the chat.
- **Portability:** hardcode nothing (no project names, people, counters) — everything is derived from the files at render time.
- **No ranking** (rule 10): no top 3, no focus claim.
- **Empty sections collapse:** unused placeholder = empty string, no empty card. A placeholder NEVER stays unreplaced.
- **Invent nothing:** values come from PROJECTS.md, STATUS.md, JOURNAL.md, config.yaml and the mail/calendar state of the run. HTML-escape texts, no em-dashes in user copy.

**Language:** the visible texts below (column values, labels, section headings inside fragments) are generated at render time and follow `config.yaml → language` — they are NOT hardcoded anywhere. Everything shown here is an English **example**, not a fixed string. Structural names — placeholder tokens, CSS classes, HTML ids, data-attribute NAMES — are fixed and never translated; data-attribute VALUES are the fixed English keywords listed per placeholder.

## Mechanism

1. Compose every placeholder value as a short HTML fragment (or empty string).
2. Write the fill script to `_tmp/fill.js` (or `_tmp/fill.py`) and run it with `config.yaml → script_command` (order: `node`, `uv run python`, `python3`, `python` — the language follows the command; empty/failure → try them in order, never hardcode). Script: read template, `replace` per placeholder, write `today.html`. If everything fails → only the dashboard drops out, never the briefing (say it once in the chat, carry on).
3. **Failure modes:** template missing/broken → run the briefing anyway, say so honestly ("context/today_template.html is missing — restore it from the original copy; until then everything else works normally"). The template is source code, not reconstructable.

## Placeholders and what fills them

- `{{USER_NAME}}` — `user.name` from config.yaml (dashboard header).
- `{{GENERATED_AT}}` — **honest age, no clock cosmetics**: rendered today → `07:41`; older → `3 days ago`. A dashboard that shows "07:41" although the state is from Monday is lying.
- `{{DATE_LONG}}`, `{{DATE_ISO}}`, `{{GENERATED_AT}}` — today's date (long form + ISO for the localStorage key + generation time).
- `{{META_LINE}}` — one neutral line of counts, e.g. `N tasks open · N in the inbox · N projects · N tickets` — counts only, no "this is what matters" framing.
- `{{BRIEFING_LEAD}}` — **ONE sentence** (max ~16 words) that puts the day in a nutshell: what shapes it, what it leads up to. Renders twice: collapsed as the teaser line, expanded as the big lead sentence above the text (one fragment, two places — the template does that). **Descriptive, no judgement/ranking** (rule 10): "Four meetings today, the steering prep at 2 pm" ✓ — "Your most important task today is X" ✗. Plain and concrete — no imagery ("frame the day"), no filler ("at the centre stands"). No lead → the block hides itself entirely.
- `{{BRIEFING}}` — **the highlight of the Today tab** (renders under the lead in the expandable block): 2–4 short `<p>` paragraphs that tell the day CONVERSATIONALLY — like a good chief of staff briefing you for 30 seconds in the morning. **ONE continuous line of thought**, not topic nuggets: how the day runs (meetings + what they lead up to), what came in from the mail overnight, what is due per project (descriptive, NO ranking), watch-outs woven in instead of listed. **Concrete tone:** short sentences, real names and numbers, no abstractions and filler words ("at the centre stands", "it is a matter of", "shapes", "in particular", "in the context of") — like a colleague at the coffee machine telling you in 30 seconds what is going on today.
  **Inbox duty:** the morning's mail findings belong in the text — and recognisably as *not yet processed*, with the way out. Example: "Both are sitting in your inbox: tell me which project they should go to, or throw them away." Without that sentence the user does not know that the inbox lines need a decision from them.
  **Mandatory signals — these three kinds of information must appear** (woven into the prose, no lists; an empty category drops out without comment, no "nothing to report"):
    1. **New from the mail:** what came in and needs a decision — the inbox findings with sender and core point ("Thomas is only sending the raw data on Wednesday, which pushes the analysis out by two days").
    2. **Where you are waiting:** every `(waiting on X)` task and every ⏳ thread past `waiting_overdue_days` — with name and age ("on the ERP migration you have been waiting four days for the interface documentation").
    3. **Due today + overdue:** every task that is due today or whose `(due DD.MM.)` lies in the past — by name, without judgement, without alarmism. Those are the lines the user is most likely to miss in the list below.
  **Completeness of these signals beats elegance** — better one sentence more than an overdue task that only appears in the list. That is also why the cap is raised: max ~220 words.
  Names/projects in `<strong>`. NO repetition of the lead sentence. No icon staccato, no bullets — prose. The metrics column (meetings/mails/due items) is counted by the template itself — do not write it along.
- `{{AGENDA}}` — the day as a **timeline** (renders large in the Calendar tab, "Your day"), one lean `<li>` per meeting:
  `<li class="ev" data-time="HH:MM" data-end="HH:MM"><b>HH:MM</b> Title <i class="ic ic-video"></i>[<details class="mb"><summary>Briefing</summary><div class="mbc">…</div></details>]<i>Context blurb from step 2a-2</i></li>` — **the order is binding: title, format icon, briefing button, THEN the context line.** The context line is a block element; if the briefing button sits behind it, it drops into a third line and gets clipped by the block on short meetings (the meeting block is as tall as its duration, `overflow: hidden`). Then nobody sees that a briefing exists. **Format icon instead of an emoji:** `<i class="ic ic-video"></i>` for remote meetings, `<i class="ic ic-bldg"></i>` for in-person, none at all when unclear. Never use an emoji for it, the template has SVG. Priority via the class `p-red`/`p-amber` on the li (⚪ = no class). The `<i>` sub-line only when a context blurb exists; the `<details class="mb">` only when a meeting briefing exists (step 2a-2 point 2b). **Structure of the `.mbc` content** — lead as running text, then only the sections with substance:
  `<p class="mb-lead">1–2 sentences on what it is about</p><div class="mb-grid"><section><h4>Where it stands</h4><p>…</p></section><section><h4>Expected from you</h4><ul><li>…</li></ul></section><section><h4>To clarify</h4><ul><li>…</li></ul></section><section><h4>Who is attending</h4><p>Name (role) · Name (role)</p></section><section><h4>Last time</h4><p>DD.MM. · …</p></section></div>`
  The template lays the sections out in two columns automatically and lets the panel scroll when there is a lot of content.
  **The switch is the time, not the meeting type** (reminders from step 2a are usually timed, not all-day):
  - **anything with a time** → onto the timeline, with `data-time` + `data-end`. Reminders additionally with the class `rem`: `<li class="ev rem" data-time="HH:MM" data-end="HH:MM"><b>HH:MM</b> Title</li>` — the template draws them dashed, counts them as reminders instead of meetings and never gives them the "running"/"up next" marker.
  - **all-day, without a time** → `<li class="ev rem"><b><i class="ic ic-cal"></i></b> Title</li>`, **no** `data-time`, **no** `data-end`. The template hangs it below the timeline.
  **`data-end` is mandatory for everything with a time** (source: step 2a, the end of the meeting). From it the template draws the block height and the free gaps ("2 hrs free") and places overlapping meetings side by side. If it is missing, the template assumes 30 minutes — the timeline then no longer matches the calendar.
  **Do not compute any of this at render time:** dimming the past, marking "running"/"up next", setting the now line and generating the duration labels is done client-side by the template — only that way does it stay correct all day without `/morning` running again.
- `{{AUDIT}}` — Audit tab. **Never written by hand**: the fragment comes from `node reference/scripts/workspace-audit.js --render`, which only reads the finished `context/audit.json` and therefore costs nothing. The audit RUN itself never happens inside `/morning`, only on `/audit`. No `audit.json` yet → the script emits a calm empty-state card with the sentence to say in the chat.
- `{{SELBSTTEST}}` — **Workspace** tab, block "What is still open on your system" (`.health`, ABOVE "Your memory, live"): one `<li>` per open item from the self-test (`reference/self-test.md`, filled by `/morning` step 6a), in plain language exactly as the checklist prescribes — `<li><b>Short label:</b> consequence + what the user can say</li>`. Nothing open → empty string, the block hides itself (`data-collapse-empty`). Mid-day re-render: repeat the level A checks briefly (local file checks only, costs nothing) instead of blindly carrying over the morning state.
- `{{TASK_ITEMS}}` — **the single unified task list from step 4**, already merged and tagged there. Each item is lean:
  **Table rows with 5 cells** (the column header is static in the template):
  `<li data-id="..." data-project="..." data-status="todo|waiting" data-cat="deep-work|quick-win|comms|prep|admin"[ data-due="YYYY-MM-DD"][ data-plan="1"][ data-note="1"]><span class="t-text">Task text[ <a class="mail" href="...">Mail</a>]</span><span class="c-proj">Project</span><span class="c-cat">Deep Work</span><span class="c-status">waiting on X|open</span><span class="c-due">DD.MM.</span>[<div class="t-note">1–3 sentences of context</div>]</li>`
  **The task text comes WITHOUT the suffixes `(due …)` and `#category`** — both live in their columns (`data-due`/c-due, `data-cat`/c-cat); in the text they would be duplicated and make the row restless.
  **`data-note` + `<div class="t-note">`** — the task row carries the **headline**, the note the **executive summary** (the template turns it into the click-to-expand). Source: the indented line under the STATUS.md bullet. **The rule, not the exception** — a task without an explanation is worthless to the reader in two weeks. The only exception: the note would merely rephrase the headline ("submit travel expenses" → "the travel expenses have to be submitted") — then leave it out, filler sentences are worse than nothing.
  — display rows only, no checkbox markup. Leave empty cells as empty `<span>` (the template shows "–"). `data-due` mandatory wherever a date exists (the time filter/Calendar tab compute with it; the overdue red is done by the template); `data-plan="1"` on tasks from STATUS.md's day plan (green plan dot). No cap, no sort-by-importance.
- `{{INBOX_ITEMS}}` — inbox rows in their OWN card (`#inbox-list` in `.inboxbox`, directly above the task list, framed amber). Same row markup as the tasks: `<li data-id="in1" data-inbox="1" data-project="Inbox" data-status="unconfirmed" data-cat="comms" data-note="1"><span class="t-text">1-line core point<span class="tag inbox">Inbox 1</span>[ <a class="mail" href="...">Mail</a>]</span><span class="c-proj">Inbox</span><span class="c-cat">Communication</span><span class="c-status">unconfirmed</span><span class="c-due"></span>[<div class="t-note">Sender · for X</div>]</li>` — running number (for "take 1"). **Text = only the core point + the number tag (+ mail link for mail findings); sender and age move into the `t-note`** — the same rule as with the tasks: one fact per place, the row stays readable. (Chat notes: no mail link, note = "from the chat · for X".) Empty string = the whole card hides itself (`data-collapse-empty`). **The inbox is deliberately NOT filtered and NOT sorted** — it is a decision zone, not a work list; filters and due-date sorting apply only to the task list. Note expansion, overdue red and the metrics line apply to both lists though (template helper `allRows`).
- `{{PLAN_STATE}}` — attributes for the progress line, counted from the `## Day Plan` section: `data-done="N" data-total="M"` (done = ticked checkbox). If the date line below it is not from today or there is no plan → empty string, the line stays hidden.
- `{{EMAIL_STATUS}}` — ONE inline footer line, non-actionable mail housekeeping only: `Tickets open N · FYI N[ · 🔒 N sensitive]`. Anything actionable from mail is NOT duplicated here — it already went into `{{INBOX_ITEMS}}` (step 4B), where it waits for the user's decision.
- Watch-outs have NO dashboard element of their own (no permanent banner): nuances/ambiguities from the triage (e.g. a reply that may not fully cover the question) are woven conversationally into `{{BRIEFING}}` — where the day is being told anyway.
- `{{AUDIT_FOOTER}}` — one line: `X mails checked · M of them already triaged · Y ticket threads grouped · Z newsletters/notifications left out · N of your own sent mails skipped`. Omit any segment whose count is 0.
- `{{OWN_TOOLS}}` — Workspace tab, section "Your own tools". Per entry under `own_tools` in `context/config.yaml` (fields `name`, `purpose`, `url`, optionally `category`) one tile: `<a class="tool" href="{url}" target="_blank" rel="noopener">[<code>{category}</code>]<h3>{name}</h3><p>{purpose}</p><p class="say">{url}</p></a>`, the `<code>` only when `category` is set. List empty or missing → empty string, the template puts its own hint there. Invent nothing: only carry over what is in the config.
- `{{TOOLS_EXTRA}}` — Workspace tab, section "Additionally available". The guide + the 4 package tools are STATIC in the template (do not generate them!). Here ONLY what the user has added themselves. **The distinction is made by rule instead of by a name list** (a list of the bundled skills would have to be maintained on every package update and would have to be read along on every render): glob `.claude/skills/*/SKILL.md`, and of those only the ones whose `SKILL.md` is **newer than `VERSION.md`** — everything that came with the package carries the copy stamp of the delivery and thus drops out. When in doubt (same time, no `VERSION.md`) a skill counts as bundled, better one tile too few than a wrong one. Per hit a `<div class="tool"><code>/name</code><h3>Title</h3><p>1 sentence, distilled from the `description` in the frontmatter (read the frontmatter only, never the body)</p></div>`. Nothing found → `<div class="tool"><h3>Nothing added yet</h3><p>You can install further skills or plugins at any time. Tell Claude what you need.</p></div>`. **Always additionally these two cards at the end** (they are not skills but reference works; both static, literally like this). **These texts are user copy: full sentences, no em-dashes, one topic per card** — the same rule as in the template:
  1. `<div class="tool"><h3>Connect mail and calendar</h3><p>How you connect mail and calendar, what gets read in the process and what never happens. It is in <code>reference/mcp.md</code>.</p><p class="say">"How do I connect my mailbox?"</p></div>`
  2. `<div class="tool"><h3>What this system does</h3><p>One page in plain language: what Claude reads, and what never happens. It sends no mail, changes no appointment and leaves HR topics out entirely. It also holds the ready-made paragraph for the case that someone asks you whether you are allowed to use this.</p><p class="say">"What does the system actually read?"</p></div>`
  3. `<div class="tool"><h3>Version and contact</h3><p>Which version you have, and who built it. If something is broken, get in touch with the version number: it may well have been fixed long ago.</p><p class="say">"Who built this?"</p></div>`
- `{{COMMANDS_USED}}` — Workspace tab, the list "Recently used" below the command cards. **Only provable data from existing traces, invent nothing:** `/morning` → the date of the most recent `inbox/briefing-*.md` (including `inbox/archive/**`); `/eod` → the most recent JOURNAL day date whose entry has real bullets (not the empty morning slot); `/ingest` → the most recent file in `inbox/processed/` or `projects/*/inputs/` (date prefix); `/email` → "style learned" if `EMAIL_STYLE.md` exists, a date only if a `_tmp` draft artefact supplies one. Format per line: `<div class="cmduse"><code>/morning</code><span>last run today 07:31</span></div>`. **The amber "a while ago" chip EXCLUSIVELY for `/morning` and `/eod` beyond 14 days** — `/ingest` and `/email` are demand-driven, long pauses there are normal and are never flagged. No trace present → for morning/eod "never run yet", for the others the line without a date. Cheap (local file dates only), do not cache.
- `{{MEMORY_FILES}}` — Workspace tab, section "Your memory, live". One line per working file in `context/`, in this order: STATUS.md (the work), PROJECTS.md (the projects), JOURNAL.md (the history), PERSONAL.md (who you are), config.yaml (your values), EMAIL_STYLE.md (your mail style, **only if the file exists**). Format exactly: `<div class="memrow"><code>STATUS.md</code><span>PURPOSE</span><span class="memwhen">updated X AGO</span></div>` — PURPOSE is a short half-sentence, "X AGO" comes from the "Last updated:" line of the file (mtime as fallback), phrased colloquially ("earlier today", "3 days ago"). No line counts, no paths. If a file is missing, leave the line out. Cheap, do not cache.
- **The skin switch is not your business.** The dashboard has two looks (normal and pixel), toggled by the button at the top right and remembered in the browser. That is CSS in the template, it changes no fragment and no placeholder. Never render two files, never ask which look someone wants.
- `{{AUSSTATTUNG}}`: Workspace tab, section "Your setup" — **the overview of what is wired up here**, as KPI tiles: a wide **Startup setup** progress tile (percentage of required steps done, opening into the checklist) plus **Skills · MCP · CLI · Repos · Plugins · Routines · API keys**, each opening into its list. The percentage counts ONLY the fixed setup checklist, never whatever else the user has on their machine; a slot counts as filled by any route (connected MCP server OR an installed CLI doing the same job). **Do not write this fragment yourself. Run the script:**

  ```
  node reference/scripts/inventory.js
  ```

  It prints the finished HTML to stdout. In the fill script take the output straight as the value of the placeholder (`require('child_process').execSync('node reference/scripts/inventory.js').toString()`) — that way the content never passes through your context and never costs tokens. If `script_command` is not node, run the script separately via Bash and paste the output in. If node is missing entirely, leave the placeholder unreplaced: the template shows its own calm hint per category.

  **What the script reads, so that the overview is right instead of merely maintained:** skills from `.claude/skills/*/SKILL.md` (name + first sentence of the description), locally registered MCP servers from `claude mcp list` (merged with `inventory.connectors` from `config.yaml`, whose wording wins), tools from `inventory.clis` **with a live `command -v` check**, repos from `inventory.repos` plus the git remote of this folder (the workspace card carries `backed up X ago` from `git log`), access keys from `inventory.accounts` (only the presence of the NAME in `~/.config/credentials.env`, never the value), plugins and routines from the config (routines with a sign of life from the newest matching result file in `inbox/`, amber `may no longer run` beyond 2 days). Connectors wired up in Claude Cowork do not appear in `claude mcp list` — they only exist in `config.yaml`, which is why both sources are merged.

  **Consequence for `status:` in the config:** for `clis`, `accounts` and locally registered MCP servers it is decorative, the live check wins. Do not maintain drift by hand, do not write it back. Only `purpose` genuinely matters — it is what makes the card readable ("what is this thing here for?").

  **Cheap and always fresh:** local files plus one `claude mcp list`, no mail, no calendar, no cost worth mentioning. Generated fresh on EVERY re-render, does NOT belong in `.mail_cache.json`.

- `{{PROJECT_DETAIL}}` — one `<article class="pdetail" data-health="green|amber|red">` per project, fixed order, omit empty building blocks entirely: 1. `<div class="head"><h3>Name</h3><span class="badge …">Phase</span></div>` · 2. `<p class="p-about">` 1 sentence on what it is about · 3. `<p class="story">` 2–4 sentences, conversational (state, what happened last, what is next — for non-specialists) · 4. `[<p class="blocker-line">Blocker + since when + who</p>]` · 5. `[<h4>Open to-dos</h4><ul>]` max 5, exactly the task texts · 6. `[<h4>Recent decisions</h4><ul>]` max 4 with date · 7. `<div class="p-spacer"></div>` always · 8. `[<p class="p-time">Milestones</p>]`. Sources: PROJECTS.md + project README (already read, no extra fetch).
- `{{BRIEFING_SECTIONS}}` — up to three collapsible sections **below** the briefing text. Each one: `<details class="brf-sec"[ open]><summary><span class="bs-title">TITLE</span><span class="bs-count">N</span></summary><div><p>…</p></div></details>`. The FIRST rendered section carries `open`, the rest stay collapsed. **A section with nothing to say is left out entirely** — never an empty shell, never "nothing here today".

  | Section | Title | What goes in it | Where it comes from |
  |---|---|---|---|
  | 1 | `Waiting on` | Per item ONE sentence: on whom, **since when** (absolute date plus the number of days), and **what happens if it does not come**. That last part is the whole point — the task list already knows the what, it does not know the consequence. | Tasks tagged `(waiting on X)` in STATUS.md + the "Waiting" bucket of today's triage |
  | 2 | `Since yesterday` | What actually moved: an answer that arrived, a decision that was made, something that got done. Past tense, no to-dos. | The most recent JOURNAL.md entry + today's mail findings + "Recently done" in STATUS.md |
  | 3 | `Today and overdue` | The tasks that carry a date of today or earlier, **verbatim from STATUS.md**, each as `<p><b>Task text</b> · due DD.MM.[ · N days over]</p>`, oldest first. Plus, where it is known, half a sentence on what hangs on it. Nothing dated → the section is left out. | The `(due DD.MM.)` suffixes in STATUS.md, plus blockers from PROJECTS.md |

  **Sections 1 and 2 never restate a task** — they carry what the list cannot: since-when, consequence, what changed. If either would only rephrase the task list, leave it out.

  **Section 3 is the one deliberate exception, and it has a rule.** It shows the same tasks that are in the list below, because "what is due today" is the one question you should not have to scroll for. That is allowed because the criterion is **objective**: a date the user set themselves, not an assessment by Claude (CLAUDE.md rule 10 stays intact — this groups by date, never by importance). To keep the copy from drifting, the task text is taken **verbatim** from STATUS.md, never rephrased, never shortened. And the list below stays the place where things get ticked off; this section only shows, it never becomes a second truth.

  **`N` is the count of items in that section**, so the collapsed state already says how much is behind it. Nothing to report at all → `{{BRIEFING_SECTIONS}}` is an empty string and the block disappears.
- `{{NOTES}}` — `<li><b>DD.MM.</b> Note text</li>` from JOURNAL.md (### Notes entries + free insight bullets), the last 14 days, newest first, max 10; empty string collapses the block.

## Mail/calendar cache (mid-day refresh)

After the morning render write `context/.mail_cache.json` — **`"date": "YYYY-MM-DD"` as the first field** (without a date nobody spots yesterday's state) and **`"mail_checked": true|false`** (false = fast mode / degraded without the mailbox; the mail fields are then empty and must not be reported as state). Content: `{{EMAIL_STATUS}}`, `{{AGENDA}}`, `{{INBOX_ITEMS}}`, `{{BRIEFING}}` + their counts.

**Mid-day re-render (chat update, CLAUDE.md rule 1):** fresh `{{PROJECT_DETAIL}}`/`{{NOTES}}`/`{{TASK_ITEMS}}`/`{{PLAN_STATE}}` from the files + mail/calendar state from the cache — **never rescan mail/calendar**. `{{AUSSTATTUNG}}`, `{{COMMANDS_USED}}` and `{{OWN_TOOLS}}` are cheap (config.yaml, local file dates and the cache stamp only) and are generated fresh on every render, so they do NOT belong in the cache. If the cache is missing or its `date` is not today → skip the refresh, no error, say it once per session in a friendly way ("Your dashboard is from yesterday — say 'good morning'"). **Never render with yesterday's data.**

## Opening (OS routing via `os` from config.yaml)

Windows: `cmd //c start "" context/today.html`, on failure → `explorer.exe context/today.html`. Mac: `open context/today.html`. If both fail → just name the path. Not blocking.
